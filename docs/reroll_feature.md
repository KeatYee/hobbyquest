# Reroll Feature

## Purpose

The reroll feature lets a learner replace an active quest when the current task does not fit their mood, context, available materials, or preferred approach.

Rerolling is designed to preserve the user's learning path while changing the surface task. The new quest should teach the same underlying skill, remain relevant to the current milestone, and keep the same progression structure.

In the current app, rerolling does not award XP, complete a quest, change milestone progress, or unlock new nodes. It only rewrites selected quest content.

## Functional Description

### 1. User-Facing Flow

The user sees a `Reroll` button on an incomplete quest card. The button uses a casino icon and appears beside the quest duration chip.

When the user taps `Reroll`:

1. The app shows a confirmation dialog.
2. The dialog title is `Reroll this quest?`.
3. The dialog explains that a new task will be generated for the same skill.
4. If the user cancels, nothing changes.
5. If the user confirms, the app calls the reroll controller method.
6. Gemini generates an alternative version of the quest.
7. The quest document is updated in Firestore.
8. The active plan is reloaded.
9. The quest list refreshes in the UI.
10. The app shows either a success dialog or an error dialog.

Success message:

```text
Quest rerolled
The new quest version has been saved.
```

Failure message:

```text
Reroll unavailable
Unable to reroll this quest right now
```

### 2. What Changes During Reroll

The persisted single-quest reroll updates these fields:

- `title`
- `desc`
- `steps`
- `youtube_search_query`

These fields are generated by Gemini as the alternative task content.

### 3. What Stays the Same

Reroll keeps the quest's structural and progression identity.

The following fields are not intentionally changed:

- Quest ID / node ID
- Quest type
- XP reward
- Duration minutes
- Dependency list
- Active state
- Completion state
- Reflection note
- Completion timestamp
- Image evidence
- AI feedback fields
- Milestone index
- Plan ID

This means the rerolled quest remains in the same position in the skill graph. Any future quests that depend on this quest continue to depend on the same node ID.

### 4. Reroll Prompt Rules

Gemini is asked to generate exactly one alternative quest.

The generated quest must:

- Teach a similar underlying concept.
- Belong to the current milestone.
- Use a different approach or mechanic from the rejected quest.
- Keep the same quest type.
- Take approximately the same duration.
- Return a title, description, five steps, and a YouTube search query.

Quest type is preserved by passing the current quest's type into the prompt:

- `knowledge`: theory or observation task.
- `practice`: hands-on drill.
- `challenge`: boss-level practical task that still requires photo proof when completed.

Duration is preserved by passing the current `durationMinutes` into the prompt.

### 5. Active Persisted Reroll

The main implemented reroll flow is single-quest and persisted.

It is triggered from:

```text
HomePage quest card
  -> HomeController.rerollQuestWithGemini(questId)
```

This is the flow users currently access from the quest card UI.

### 6. Older Ephemeral Reroll

There is also an older method:

```text
HomeController.rerollWithGemini()
```

This method loops through all currently loaded `dailyQuests`, generates alternatives, and updates only local reactive state:

```text
dailyQuests.value = refreshed
```

It does not write to Firestore. The code comment explicitly says it is ephemeral.

This means the changes disappear when the app reloads the plan from Firestore. It appears to be a legacy or experimental path rather than the current user-facing reroll feature.

### 7. Refresh-Only Reroll Name

There is another similarly named method:

```text
HomeController.rerollDailyQuests()
```

Despite the name, this does not generate alternative quest content. It simply reloads the current plan's quests from Firestore and recomputes which quests are active.

Its behavior is closer to "refresh quest list" than "reroll quest."

## Technical Implementation

### 1. Key Files

Relevant implementation files:

- `lib/app/views/pages/home_page.dart`
- `lib/app/controllers/home_controller.dart`
- `lib/app/services/gemini_service.dart`
- `lib/app/models/quest_node_model.dart`
- `lib/app/services/quest_service.dart`
- `lib/app/models/user_model.dart`

### 2. UI Entry Point

The reroll button is rendered inside `_buildQuestCard` in `home_page.dart`.

The button:

- Is a `TextButton.icon`.
- Uses `Icons.casino_rounded`.
- Displays the label `Reroll`.
- Shows a confirmation dialog before calling the controller.

The relevant call is:

```text
controller.rerollQuestWithGemini(questId)
```

The UI relies on the returned boolean:

- `true`: show success dialog.
- `false`: show error dialog.

### 3. Controller Method

The main persisted reroll method is:

```text
Future<bool> HomeController.rerollQuestWithGemini(String questId)
```

It performs these steps:

1. Checks whether Gemini has an API key.
2. Looks up the target quest from `dailyQuests`.
3. Calls `GeminiService.generateAlternativeQuest`.
4. Checks the current Firebase Auth user.
5. Checks the active plan ID.
6. Extracts generated steps and YouTube search query.
7. Updates the quest document in Firestore.
8. Reloads the plan, milestones, and quests from subcollections.
9. Reloads the user document.
10. Rebuilds the in-memory `UserModel`.
11. Updates local reactive profile and quest state.
12. Recomputes quest active states using `getAllQuestNodes`.
13. Updates `lastRerollDate` on the user document.
14. Returns `true`.

If any required state is missing or an exception occurs, it logs the error and returns `false`.

### 4. Firestore Write

The reroll write targets the existing quest document:

```text
users/{uid}/plans/{planId}/quests/{questId}
```

The update payload is:

```text
{
  title: generatedTitle,
  desc: generatedDescription,
  steps: generatedSteps,
  youtube_search_query: generatedYoutubeSearchQuery
}
```

The code does not create a new quest document. It overwrites fields on the existing quest document.

### 5. Firestore Reads After Write

After updating the quest, the controller reloads:

```text
QuestService.loadQuests(uid, planId)
QuestService.loadPlan(uid, planId)
QuestService.loadMilestones(uid, planId)
users/{uid}
```

Then it rebuilds the current plan:

```text
fullPlan = plan.copyWith(
  milestones: milestones,
  quests: quests,
)
```

Then it rebuilds the user:

```text
updatedUser = UserModel.fromJson(data, uid).copyWith(
  activePlanId: planId,
  currentPlan: fullPlan,
)
```

Finally, it updates GetX reactive state:

```text
user.value = updatedUser
nickname.value = updatedUser.nickname
avatarSvg.value = updatedUser.avatarSvg
hobby.value = updatedUser.currentPlan.hobby
goal.value = updatedUser.currentPlan.goal
learningPace.value = updatedUser.currentPlan.learningPace
level.value = updatedUser.currentPlan.level
dailyQuests.value = getAllQuestNodes(updatedUser.currentPlan.quests)
```

### 6. Reroll Timestamp

After the reroll succeeds, the controller writes:

```text
users/{uid}.lastRerollDate = DateTime.now()
```

`UserModel` includes `lastRerollDate`, and reads/writes it during serialization.

Currently, this field is only recorded. The code does not enforce a cooldown, daily limit, reroll count, or paid reroll system from this timestamp.

### 7. Gemini Service Method

Alternative content is generated by:

```text
Future<Map<String, dynamic>> GeminiService.generateAlternativeQuest(...)
```

Inputs:

- `hobby`
- `nodeTitle`
- `nodeDesc`
- `learningPace`
- `milestoneTitle`
- `questType`
- `durationMinutes`

Expected output:

```text
{
  title: string,
  desc: string,
  steps: string[],
  youtube_search_query: string
}
```

The method extracts a JSON object from Gemini's response and normalizes missing fields.

For missing fields after a successful response:

- Missing title falls back to an internal alternative title.
- Missing description falls back to `Complete a focused step for {hobby} today.`
- Missing steps fall back to a short generic three-step list.
- Missing YouTube query falls back to `{hobby} {oldQuestTitle}`.

### 8. Fallback Behavior

`GeminiService.generateAlternativeQuest` has an internal no-key and failure fallback:

```text
_getAlternativeTaskFallback(hobby, currentTask)
```

Fallback choices are random:

- `Alternative Study`: watch a short video explaining the current task.
- `Mental Reps`: visualize the steps required to complete the current task.
- `Break it Down`: write down the hardest parts of the current task.

Important current behavior:

- `HomeController.rerollQuestWithGemini` checks `hasApiKey` before calling Gemini.
- If the API key is missing, the controller returns `false`.
- Because of that controller check, the no-key fallback inside `GeminiService` is not reached by the current quest-card reroll button.
- The fallback is still useful for callers that invoke `GeminiService.generateAlternativeQuest` directly or if the API fails after the controller has already passed the API-key check.

Another current edge case:

- If Gemini throws and the service returns `_getAlternativeTaskFallback`, that fallback only contains `title` and `desc`.
- The controller then persists `steps: []` and `youtube_search_query: ''` because those fields are absent.

### 9. Backward-Compatible Title-Only Method

There is a compatibility wrapper:

```text
Future<String> GeminiService.generateAlternativeQuestTitle(...)
```

It calls `generateAlternativeQuest` and returns only the generated title. This exists for older callers that expected a title string instead of a full quest-content map.

No current user-facing reroll path appears to use the title-only method.

### 10. Data Model Impact

`QuestNodeModel` supports all reroll-relevant fields:

```text
nodeId
title
desc
steps
xpReward
type
durationMinutes
dependsOn
isCompleted
isActive
reflectionNote
completedAt
imageUrl
greeting
observation
tip
youtubeSearchQuery
```

Because reroll only writes title, description, steps, and YouTube query, all other model fields survive the update in Firestore.

### 11. Interaction With Quest Graph

The quest graph is preserved during reroll.

Because `node_id` and `depends_on` are unchanged:

- Rerolling a root quest keeps it a root quest.
- Rerolling a locked quest would keep it locked.
- Rerolling an active quest keeps it active.
- Downstream quests that depend on the rerolled quest are unaffected.

After reload, `getAllQuestNodes` recomputes `isActive` based on completed dependencies.

### 12. Interaction With Completion and XP

Rerolling does not:

- Mark the quest complete.
- Award XP.
- Change the user's level.
- Change streaks.
- Change category XP.
- Advance milestones.
- Change tree growth.

XP is still awarded only when the quest is completed through the quest detail completion flow.

If a rerolled quest is later completed, it awards the same XP reward as before, because reroll does not change `xp_reward`.

### 13. Current Limitations

Current limitations and risks:

- There is no reroll cooldown despite `lastRerollDate` being recorded.
- There is no reroll count or cost.
- There is no per-quest reroll audit history.
- There is no transaction around the quest update plus `lastRerollDate`.
- If the quest update succeeds but timestamp update fails, content still changes.
- If the timestamp update succeeds after a partial failure in future edits, it may not reflect a saved content change.
- The active UI path returns failure when no Gemini API key exists, even though the service has a fallback generator.
- Fallbacks from API failure may save empty steps and an empty YouTube query.
- The controller looks up quest details from `dailyQuests`; if the target quest ID is not currently loaded, it falls back to empty title/description, `practice`, and `15` minutes.
- The comment says the reroll button is hidden when locked, but `_buildQuestCard` itself does not enforce that. The main home list only passes active quests, so the button is effectively shown for active incomplete quests there.
- The reroll write does not validate that the generated steps list has exactly five items before saving.
- The reroll prompt asks Gemini not to duplicate the old task, but the app does not programmatically compare old and new content.

## Acceptance Criteria

A complete persisted reroll should satisfy:

- The user must confirm before rerolling.
- Canceling the confirmation dialog leaves the quest unchanged.
- Confirming reroll generates a new title and description.
- The same quest document is updated instead of creating a new quest.
- The quest keeps the same node ID.
- The quest keeps the same type.
- The quest keeps the same XP reward.
- The quest keeps the same duration.
- The quest keeps the same dependencies.
- The quest keeps the same completion state.
- The quest list refreshes after the Firestore update.
- The UI shows a success message after a saved reroll.
- The UI shows an error message when reroll cannot run.
- `lastRerollDate` is updated after a successful reroll.
- Rerolling does not award XP.
- Rerolling does not affect streaks, milestones, category XP, or tree growth.

## Recommended Improvements

Recommended implementation improvements:

- Decide whether no-key fallback should be user-facing. If yes, remove the early `hasApiKey` return in the controller.
- Save non-empty fallback steps and YouTube query when Gemini fails.
- Add a reroll cooldown or remove `lastRerollDate` if it is only diagnostic.
- Add a `rerollCount` or `rerolledAt` field on individual quest documents.
- Store previous quest versions for audit/history.
- Validate generated output before saving.
- Prevent rerolling completed quests at the controller level.
- Prevent rerolling locked quests at the controller level.
- Wrap quest update and `lastRerollDate` update in a single batch or transaction.
- Rename `rerollDailyQuests` to `reloadCurrentPlanQuests` or similar, because it does not generate new quest content.
